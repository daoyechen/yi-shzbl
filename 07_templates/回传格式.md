# 回传格式（所有派包通用）

> 每份任务书引用本文件，不必各写一遍。

## 一、只交 `交付/`

回传包里**只有 `交付/` 一个目录**。

| 交 | 不交 |
|---|---|
| `交付/` 里的数据文件 | 任务书（我方有原件） |
| 处理日志 | `数据/`（电子书、骨架、契约——原样在我方） |
| 质量报告 | `工具/`（自检脚本我方有） |
| 自检输出 | 任何原件扫描、PDF、图片副本 |

理由：派发包 5.3 M 里有 3.9 M 是书页 PDF，这些我方本来就有。全打回来只是把同一个文件搬两遍。实测只交 `交付/` 时，回传包 **332 K**，是派发包的 1/16。

**回传包内不要出现第二层 `交付/`。** 正确结构：

```
伤寒_注释本结构化_批次2_唐容川_金匮_1_2_批3_第3版_回传.zip
└── 交付/
    ├── 转录全文_批1.md
    ├── 转录全文_批2.md
    ├── 转录全文_批3.md
    ├── 质量报告_三批.txt
    ├── 处理日志_三批.txt
    └── 自检输出.txt
```

## 二、必交四件

| 件 | 内容 | 不交的后果 |
|---|---|---|
| **数据** | 按任务书格式产出的文件 | 无法验收 |
| **处理日志** | 做了什么、卡在哪、哪些没核 | 我方要重新猜你的边界 |
| **质量报告** | 自检跑了什么、结果多少、有哪些已知缺陷 | 无法判断是否达标 |
| **自检输出** | 自检脚本的原始终端输出 | 同上 |

## 三、处理日志怎么写

**必须写「没做什么」，不许只写「做完了」。**

反面例子（真实出现过）：

> 对图记录：逐字过，未见需改。

实际抽两页核，一页 31 处错、一页 20 处。这句"逐字过"让整份记录失真，比不交更坏。

正面例子（同一批的另一版）：

> 实做 5 页逐字对图（p11／p12／p23／p24／p40，174 处改动）。
> 其余 81 页**未逐字对原图**，逐页标「未核」。
> 能力边界：每页 20–50 处错，86 页约需 500–900 轮工具调用，一次对话做不完。

这份日志让我方一眼知道哪些能用、哪些要补，**不合格但可信**。

格式建议：

```markdown
## 做了什么
- 页范围、批范围、处理条数

## 怎么做的
- 用了什么工具、什么方法、关键判断依据

## 没做什么（必填）
- 未覆盖的页/条，逐页标「未核」
- 哪些是推断而非核对（注明"未对图"）

## 已知缺陷
- 自己发现的错、不确定的地方、可能的风险
```

## 四、命名

`<书>_<任务>_<批>_<版本>_回传.zip`，例：

```
伤寒_注释本结构化_批次2_唐容川_金匮_1_2_批3_第3版_回传.zip
```

版本号只在退回重做时加（第2版、第3版）；首版不带版本号。

## 五、我方收到后怎么处理

| 落在哪 | 什么 |
|---|---|
| `40_return/41_return_tmp/` | 解压出的原件、过程稿，验收完即清 |
| `40_return/49_return_persistence/` | 验收通过的数据、报告、校正表，永久留、入库 |
| 跨批累积的定稿 | `50_data/51_notes/`（注本）或 `50_data/52_l1_assembly/`（总装） |

回传包本身（zip）不进 git，解压后即弃。
